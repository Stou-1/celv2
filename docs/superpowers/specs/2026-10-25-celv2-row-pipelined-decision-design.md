# CelV2: 行ごとに進む GPU 判定と CPU 符号化の重ね合わせ（設計）

日付: 2026-10-25

## 目的

1フレームの処理時間（入力から出力までの遅延）を縮める。いまは GPU の判定がフレーム全体で終わってから CPU の符号化が始まるため、両者が直列に並び、これが上限を決めている。GPU が判定をスーパーブロックの行ごとに仕上げ、CPU はその行が届いたところから符号化を始めることで、同じフレームの中で両者を重ねる。

### 前提（ユーザーとの合意）

- 主な目的は1枚の処理時間を縮めること（低遅延）。処理量（スループット）だけを上げる方式は目的に合わない。
- 判定（出力）は画質が落ちなければ変わってよい。ただし本設計では判定そのものを変えないので、出力はバイト単位で今と同じになる。
- デコーダとのビット一致（CelV2 の不変条件）は保つ。

### 現状（2026-10-25 の計測、bench.y4m 720p、q150、2タイル、1フレームあたり）

| 処理 | 時間 |
|---|---|
| GPU の判定（アップロード、動き探索 1.1 ms、`decision_kernel` 約 4.8 ms、待機中の GPU の起動待ちを含む） | 約 7〜8.5 ms |
| タイルの符号化（2タイル並列、実時間） | 約 6〜9 ms |
| `begin_frame`、`end_frame`、y4m 読み込みなど | 約 2 ms |

`decision_kernel` は1つのスーパーブロックを1つのスレッドブロック（256 スレッド）が受け持ち、フレーム全体を1回で起動している。各スーパーブロックの仕事が長く、全スーパーブロックがほぼ同時に終わるため、判定を上から1行ずつ渡すことができない。占有率も低い（SM あたり約 1.4 ブロック）。

## 全体像とデータの流れ

P フレームの流れ:

1. **アップロードと動き探索（GPU、フレーム全体）**: 原画と直前の復元画像をアップロードし、ピラミッドを作って動き探索を行う。今と同じで、約 1.4 ms。ここはクリティカルパスに残る。
2. **行ごとの判定（GPU）**: スーパーブロックの行を上から順に「コスト計算 → 分割の決定 → その行の結果の転送」の順で起動し、行ごとに完了の印（CUDA イベント）を記録する。全行をまとめて積むので、CPU が起動を待つことはない。
3. **受け取り（ホスト側の回収スレッド）**: 各行の完了の印を待ち、その行の結果を `SbDecision` に変換して「r 行目まで準備完了」を知らせる。
4. **符号化（CPU のタイルスレッド）**: 2 と同時に始まる。各スーパーブロックを符号化する直前に、その行の準備完了だけを待つ。
5. **後処理**: 全タイルの符号化が終わったら、今と同じく `end_frame` とストリームの組み立てを行う。

KEY フレームも同じ経路を通る（動き探索がなく、インター候補もない）。

変えないもの:

- 判定のロジック。コストは整数の和で、分割して計算しても値は変わらない。最小値の選び方（順番）も同じにする。
- 同期 API（`decide_intra` / `decide_inter`）。全行を待つ薄いラッパーとして残し、既存のテスト（GPU と CPU 参照実装の比較）はそのまま使う。

## GPU: 判定カーネルの分割

`decision_kernel` を2つのカーネルに分け、スーパーブロックの行ごとに起動する。

### `cost_kernel`（グリッド = 行のスーパーブロック数 × K）

- 1つのスーパーブロックのコスト計算（イントラ 425 ブロック × 4 モード = 1700 個、インター 896 個、合計 2596 個）を K 個のスレッドブロックで分担する。
- タスクの割り当ては、タスク番号を全ワープ数（K × 8）で割った余りで決める。64x64 のインター評価のような重いタスクが偏らないようにするため。
- タスクの一覧（ブロック番号と、モードまたはセル番号）は全スーパーブロックで同じなので、初回に一度だけ作って GPU のメモリに置く。今は毎回スレッド 0 が作っている。
- 各ブロックは自分のスーパーブロックの DC 予測値（425 個）を計算する。K 倍の重複になるが、SATD の計算量に比べて小さい。
- 結果は GPU メモリ上のコスト配列（スーパーブロックごと、候補ごと）に書く。1スーパーブロックあたりイントラ 1700 個とインター 1024 個分の `int64_t`（約 22 KB）。
- K は、1行分の仕事で GPU を満たすように決める。K = ceil(2 × SM 数 / 1行のスーパーブロック数) を 1〜16 に収めた値とする（SM 170 個で、720p: 1行 20 個なので 17 → K = 16、1080p: 1行 30 個なので K = 12）。SM 数は `cudaGetDeviceProperties` から取る。

### `finalize_kernel`（グリッド = 行のスーパーブロック数）

今のカーネルの後半をそのまま移す。

- 各ブロックのインター候補の選択（セルの順で最初の厳密な最小値）
- 最良のモードの選択（イントラ DC, V, H, SMOOTH, インターの順で最初の厳密な最小値）
- 下から上への分割の決定（NONE, HORZ, VERT, SPLIT の順で最初の厳密な最小値）
- `SbOut` への木とブロックの書き出し

同じ整数のコストを同じ順で読むので、`SbOut` は今と同じになる。

### 行ごとの起動順（1本の CUDA ストリーム）

1. 行 r の `cost_kernel`
2. 行 r の `finalize_kernel`
3. 行 r の `SbOut` を固定メモリ（page-locked）へ非同期転送
4. 行 r の完了の印（CUDA イベント）を記録

既知のリスク: 1本のストリームでは、行 r+1 のコスト計算は行 r の分割決定を待つ。分割決定はスーパーブロックあたり1スレッドで直列に動くので、時間がかかれば隙間ができる。計測で隙間が見えたら、分割決定を2本目のストリームに移して並べる（最初からはやらない）。

## CPU: 行の待ち合わせとエンコーダの変更

### `RowGate`（`src/gpu/decision_map.h`、CPU のみ、CUDA にも AVM にも依存しない）

- 何行目まで準備できたかを持つ。`std::mutex` と `std::condition_variable` で作る。
- `publish(r)`: 0〜r 行目が準備できたことを知らせる。
- `wait_row(r)`: r 行目が準備できるまで待つ。エラーが記録されていれば、そのエラーを投げる。
- `fail(std::exception_ptr)`: エラーを記録し、待っている全スレッドを起こす。
- `DecisionMap` はデータのままにする。全スーパーブロック分を先に確保し、各行の中身は行が届いた時点で埋める。行の中身の書き込みは `publish` より前に行い、読み出しは `wait_row` の後に行う（ミューテックスで順序が保証される）。

### `GpuEngine`（`src/gpu/engine.{h,cu}`）

- `launch(src, ref, qindex, dm)`: アップロード、動き探索、全行の判定を積んですぐ戻る。`ref == nullptr` なら KEY フレーム。`dm` の大きさを先に整える。参照画像の CPU 側のコピー（固定メモリへの `memcpy`）はこの中で済ませるので、戻った後にエンコーダが復元画像を書き換えてよい。
- `collect(dm, gate)`: 各行の完了の印を待ち、`SbDecision` に変換して `gate.publish` する。エラーなら `gate.fail` を呼ぶ。
- 既存の `decide_intra` / `decide_inter` は、同じスレッドで `launch` と `collect` を呼んで `DecisionMap` を返すラッパーにする。

### `Pipeline::encode`（`src/pipeline.cpp`）

1. `gpu_.launch(...)`（GPU の仕事を積む）
2. 回収スレッド（`std::async`）で `gpu_.collect(dm, gate)` を始める
3. `enc_.encode(src, dm, key, &gate)`（タイルスレッドが行ごとに待ちながら符号化）
4. 回収スレッドの終了を待つ。エンコーダが失敗しても、回収スレッドを待ってからエラーを返す。

次のフレームの GPU のバッファは、今のフレームの回収が終わった後でしか使わないので、フレーム間で上書きは起きない。

### `Encoder`（`src/core/encoder.{h,cpp}`）

- `encode(src, dm, key, const RowGate* gate = nullptr)`。`nullptr` は「全行が準備済み」（今と同じ）で、既存の呼び出し元とテストは変わらない。
- `TileCoder::code_tile` でスーパーブロックの判定を取る直前（`encoder.cpp` の `sb_ = &dm_.sbs[...]`）に `gate->wait_row(sb_row)` を呼ぶ。
- タイルの分け方に関係なく、各スーパーブロックが自分の行だけを待つ。

## エラー処理

- CUDA のエラー: 回収スレッドが `RowGate::fail` で知らせ、待っているタイルスレッドはそのエラーで止まる。エンコーダはエラーを返し、待ち続けるスレッドは残らない。
- エンコーダのエラー: 回収スレッドの終了を待ってからエラーを返す。GPU のバッファが使用中のまま解放されることはない。

## テスト（実装より先に書く）

1. **出力のバイト一致**（`test_ippp`）: 新しい `Pipeline` と「同期の判定 + `Encoder`」（今と同じ）の出力が同じバイト列になること。640x360 と 202x122（端の処理）、1 / 2x1 / 2x2 タイル、IPPP と keyint あり。
2. **判定が今と同じ**: 既存の `test_gpu_intra`、`test_random_decisions`、`test_gpu_me`（GPU と CPU 参照実装の比較）が、同期ラッパー経由でそのまま通ること。
3. **`RowGate` 単体**（新規、CPU のみ）: `publish` の後に `wait_row` が返ること。`fail` で待っているスレッドが起きてエラーが伝わり、止まったままにならないこと。
4. **決定性**: 新しいプロセスで複数タイルの符号化を何度か繰り返し、毎回同じ出力になること（DCT の表の競合を確かめたのと同じ方法）。

## 成功の基準

- bench.y4m 720p と 1080p（30枚、q150、1タイルと2タイル）で、今の main とバイト単位で同じストリームになる。
- 新しいテストを含む全テストが通る。
- 720p、2タイル、定常状態のフレームで、1枚あたりの時間が今の約 20 ms から 12 ms 以下になる（目標）。一時的なタイマーと nsys で計り、GPU と CPU の重なりを前後のタイムラインで示す。届かない場合は、残っている待ちの場所を数字で示す。

## 範囲外（計測してから改めて検討する）

- 分割決定の2本目のストリームへの移動（隙間が見えた場合のみ）
- 動き探索の行単位化
- GPU のクロック設定（ユーザーの判断で変えない）
- 区間並列など、処理量だけを上げる方式
