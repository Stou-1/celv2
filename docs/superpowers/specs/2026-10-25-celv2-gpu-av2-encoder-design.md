# CelV2: GPU判定によるAV2エンコーダ（第1小プロジェクト）設計

- 日付: 2026-10-25
- 状態: 設計承認済み（レビュー待ち）
- 目的区分: 学習・研究

## 1. 目的と合意事項

### ユーザーが決めたこと
- GPU（RTX 5090）で判定するAV2エンコーダを、AVMのエンコーダに頼らず**独立に**作る（方式B）。
- 目的は**学習・研究**。速度や圧縮率の数値目標は置かず、AVMとの差を測れる状態を作る。
- 最初の小プロジェクトは**インター（Pフレーム）まで**含める。
- 規格で決まっている共通部分（算術符号、CDF、コンテキスト、動きベクトル予測、逆変換、予測）は、AVMの `av2/common` と `avm_dsp` をライブラリとして流用してよい。

### 前提（設計で決めたこと）
- 言語は C++17 + CUDA 13.3（導入済み）、ビルドは CMake/Ninja、Windows。
- AVMは v1.0.0（`%AVM_ROOT%`）。AVMの `av2/encoder` 配下の関数は呼ばない。デコーダは検証目的に限り使ってよい。
- 置き場所は `<repo>`（独立したgitリポジトリ）。nvccは日本語を含むパスに弱いため、パスに日本語を含めない。

### 成功条件（第1小プロジェクト）
1. 8bit 4:2:0 の y4m を、キーフレーム → P → P …（前方向のみ予測）でエンコードし、IVFで出力できる。
2. **出力をAVMデコーダでデコードした結果が、CelV2自身の復元フレームとフレームごとにMD5一致する。**
3. 分割、イントラモード、動き探索の判定をGPU（CUDA）で行う。
4. 720pと1080pで、AVMとの速度とBD-rateの比較表がある。

## 2. 出力するAV2の範囲

ほとんどのツールは、シーケンスヘッダの有効化フラグで「使わない」と宣言する（AVM v1.0.0 のシーケンスヘッダには、ツールの有効化フラグが約77個ある）。

| 領域 | 第1版で使うもの | 宣言で無効にするもの |
|---|---|---|
| フレーム | KEY と INTER（参照は直前フレーム1枚） | Bフレーム、TIP、複数参照、ブリッジフレーム |
| 分割 | SBサイズ固定（64x64。規格上128が必須なら128）、NONE/HORZ/VERT/SPLIT | `enable_ext_partitions`、`enable_uneven_4way_partitions`、SDP |
| イントラ | DC/V/H/SMOOTH、色差は独自モードのみ | CfL、MHCCP、MRL、DIP、IBP、エッジフィルタ、パレット、IntraBC、FSC |
| インター | NEWMV と NEARMV 系、MV精度は固定 | ワープ、OBMC、複合予測、マスク複合、BAWP、opfl、refinemv、グローバル動き、flex MV精度、adaptive MVD、MVバンク、ref_frame_mvs |
| 変換 | 各ブロックの最大変換サイズ、最小限の変換タイプ | 変換分割。ISTは任意なら無効 |
| 量子化 | 固定qindex（CQP） | delta-q、セグメンテーション、QM |
| ループフィルタ | すべて無効（デブロックは後の段階で追加） | CDEF、LR、CCSO、GDF |
| タイル | 1タイル | 複数タイル |

**規格上必須のツール**（例：IST、TCQ、DRLの候補リストなど、無効にする手段が規格にないもの）は、M1でAVMのデコーダの読み込み処理を確認して洗い出し、実装範囲に加える。必須と分かったものは、この節に追記する。

### 必須ツールの調査結果（Task 3、AVM v1.0.0 の `decodeframe.c` 6052〜6386行、`obu.c` 526〜717行）
- **シーケンスヘッダで無効にできる**：SDP、拡張分割、不均等4分割、DIP、エッジフィルタ、MRL、CfL、MHCCP、IBP、全モーションモード（INTERINTRA以降）、マスク複合、ref_frame_mvs、MVバンク、DRL並べ替え、TIP、mv_traj、BAWP、CWP、imp_msk_bld、lf_sub_pu、opfl、refinemv、BRU、adaptive MVD、MVD符号推定、flex MV精度、グローバル動き、短縮リフレッシュフラグ、スクリーンコンテンツツール（0に固定可）、CDEF、GDF、LR、CCSO、FSC、IST、inter IST、inter DDT、CCTX、TCQ、パリティハイディング、avg_cdf、拡張セグメント、タイル情報。
- **SBサイズ**：64x64を選べる（256/128/64から選択）。第1版は64x64。
- **残る（無効にする手段がない）もの**：
  - DRLの候補リスト。`def_max_drl_bits` は最小値（MIN_MAX_DRL_BITS）を使う。IntraBCのDRLビット数（`def_max_bvp_drl_bits`）も構文上は残る。
  - アスペクト比制限の構文、変換分割の構文（`reduced_tx_part_set=1` で縮小）、`enable_idtx_intra`（FSC無効時に1ビット）。
  - デブロック、量子化パラメータ、DC/AC差分の基本構文（`equal_ac_dc_q=1`、差分0）。
  - CDEFのスキップ時動作の選択（`enable_cdef_on_skip_txfm`）、`df_par_bits_minus2`。CDEFが無効でも構文上は書く。
- **プロファイル/レベル**：プロファイル 0（`MAIN_420_10_IP0`、8bitを含む）、レベル `SEQ_LEVEL_6_0`、tier 0。

## 3. 構成

### 原則
第1版は「**GPUが判定、CPUが正確に復元**」の分担にする。デコーダと復元画素を完全一致させる必要があるので、正確さはまずCPU上の参照コードで保証する。復元処理のGPU化は次の小プロジェクトで行い、CPU版とのMD5一致で検証する。

### データの流れ

```
y4m ─► [io] ─► 原画フレーム ─┬─► [gpu] 判定エンジン（CUDA）
                             │      ├ ピラミッド作成
                             │      ├ 階層動き探索（直前の原画に対して）
                             │      ├ ブロックごとのコスト（SATD + λ・推定ビット）
                             │      └ ボトムアップで分割とモードを決定
                             │            │ 判定マップ（分割木、モード、MV）
                             ▼            ▼
                        [core] CPUのエンコードループ（SBのラスター順）
                             ├ 予測（イントラ/インター、AVM共通部分）
                             ├ 順変換（avm_dsp）→ 量子化（自作の単純なデッドゾーン量子化）
                             ├ 逆量子化・逆変換（規格どおり）→ 復元フレーム
                             └ 記号の書き出し ─► [bitstream] ─► OBU ─► [io] IVF
                        復元フレーム ─► 次のフレームのインター予測の参照
```

### 各部の役割

| 部品 | 役割 | 依存 |
|---|---|---|
| `io` | y4mの読み込み、IVFの書き出し（8の倍数でないサイズはパディング） | なし |
| `gpu` | 原画を解析し、判定マップだけを出力する。近似でよい | CUDAのみ（AVMには依存しない） |
| `state` | デコーダが持つのと同じ状態（モード情報のグリッド、コンテキスト、参照バッファ）を保持する。AVMのコンテキスト関数やMV予測関数をそのまま使うための前提 | AVM共通部分 |
| `core` | 判定マップどおりにブロックをエンコードし、正確な復元を作る | state、AVM共通部分とdsp |
| `bitstream` | シーケンスヘッダとフレームヘッダの書き出し。デコーダの読み込み関数（`decodeframe.c`、`decodemv.c`、`decodetxb.c`）を鏡写しにして構文を書く。算術符号器はavm_dsp | state |
| `verify` | AVMの**デコーダ**をプロセス内にリンクし、復元結果をフレーム単位またはブロック単位で照合する | AVMデコーダ（検証専用） |

### 境界の決まりごと
- GPUとCPUの間でやり取りするのは**判定マップだけ**にする。判定アルゴリズム（SATD、機械学習など）を差し替えて実験できるようにするため。
- GPUでのイントラのコストは、周辺の復元画素の代わりに**原画**で近似する。ずれは圧縮率の悪化として出るだけで、ビットストリームの正しさには影響しない。
- 第1版のCPUループは1スレッド。タイル分割と並列化は後の段階で行う。

## 4. 検証とテスト

### 最重要の不変条件
> **CelV2が作る復元フレームと、AVMデコーダがデコードしたフレームが、フレームごとにMD5一致すること。**

| テスト | 内容 |
|---|---|
| 不変条件テスト | 小さなクリップをエンコードし、プロセス内のAVMデコーダでデコードしてフレームごとにMD5を比べる。外部の `avmdec`（`%AVM_BIN%\avmdec.exe`）でも1回確認する。マイルストーンごとに、その機能を使うクリップを追加する |
| 不一致の特定 | 最初に食い違ったフレームと、4x4ブロック単位の座標を自動で報告する |
| ヘッダのテスト | 書いたシーケンスヘッダとフレームヘッダを、AVMの読み込み関数で解析できることを単体テストする |
| GPUカーネル | SATDと動き探索を、CPUの参照実装と比べる（決定的な結果であること） |
| 失敗時の動作 | CUDAのエラーや未対応の入力は、メッセージを出して停止する。黙って別の処理に切り替えることはしない |

## 5. マイルストーン

規模の目安は、Claudeが実装しユーザーがレビューする前提での概算。

| # | 内容 | 完了条件 | 規模の目安 |
|---|---|---|---|
| M0 | 土台：CMake + CUDA + AVMのリンク + プロセス内デコーダでの検証の仕組み | 空のプロジェクトがビルドでき、AVM製のストリームをプログラム内でデコードできる | 0.5〜1日 |
| M1 | **ビットストリームの基盤**：シーケンスヘッダとキーフレーム、64x64固定、DC予測のみ、係数の符号化 | **avmdecでビット一致デコードできる**。必須ツールの洗い出しを§2に反映済み | 3〜7日 |
| M2 | イントラの判定：GPUのSATDで NONE/HORZ/VERT/SPLIT と DC/V/H/SMOOTH を選ぶ | ビット一致を保ったまま、M1より圧縮率が良い | 2〜4日 |
| M3 | インター：Pフレーム、GPUの階層動き探索、NEWMV/NEARMV、MV予測はAVM共通部分 | IPPPのストリームがビット一致する | 5〜10日 |
| M4 | 計測：AVMとの速度とBD-rateの比較（720p/1080p） | 比較レポートがある | 1日 |

## 6. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| 無効にできない必須ツールが多い | M1の規模が増える | M1の最初にデコーダの読み込み処理を調べて洗い出し、見積もりを更新する |
| AVMの共通関数が、エンコーダ側の構造体（`AV2_COMP` など）に依存している | 流用できない関数が出る | `AV2_COMMON` と `MACROBLOCKD` だけで呼べる関数を優先する。依存がある場合は、その関数だけを自前で移植する |
| AVMの規格修正（v1.0.0 以降） | 将来のデコーダと非互換になる | 第1版は v1.0.0 に固定する。比較用のデコーダも v1.0.0 にそろえる |

## 7. 範囲外（第1小プロジェクトでは行わない）

- 復元処理のGPU化、タイル並列、マルチスレッド
- ループフィルタ（デブロックは次の段階の候補）
- Bフレームと複数参照、レート制御（固定QPのみ）
- 10bit、4:4:4
