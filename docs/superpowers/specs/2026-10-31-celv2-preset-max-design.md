# CelV2 `--preset max`: 速度を無視して画質と圧縮率を突き詰めるモード（設計）

2026-10-31。予定表の 7 番。

## 目的

速度の上限を設けず、画質と圧縮率だけを追うモードを CelV2 に加える。今の既定は速さのために
「見積もりで判断する」「候補を絞る」「GOP と画質の配分を固定の規則で決める」を選んでいる。
このモードでは、それらを順に、実際に試して選ぶ方式に置き換える。

利用者が決めたこと:

- 速度の上限はない。ただし品質を落とさずに速くできるところは速くする。目で見て分からない
  程度の損失は許容する。
- 画質は PSNR-Y を主に判定し、VMAF（NEG モード、`vmaf_v0.6.1neg`）で確認する。
- 目標: まず AV1 の最も遅い設定（libaom cpu-used 0、SVT-AV1 preset 0）を全素材で超え、次に
  avmenc cpu-used 0 に近づく。
- 進め方: 「実際に符号化して比べる」方式を段階的に（案 A）。avmenc 式の全探索の作り直し
  （案 C）はしない。

## 使い方

- コマンドライン: `--preset max`。コマンドラインで個別に指定したオプションは、`--tune` と同じく
  `--preset max` より優先する（`given` の一覧で判定）。`--tune` とも組み合わせられる。
- GUI: 「内容」の右に「とても遅いが最高画質」のチェックボックスを置き、`--preset max` を渡す（「画質」は qindex の選択なので、そこには並べない）。
- 出力は常に AV2 の規格どおりで、avmdec で復号できる（今と同じテストで確かめる）。

## 段階

1. **第 1 段（この仕様書）**: GOP とフレームのフィルタを、実際に符号化して選ぶ。
2. 第 2 段（別の仕様書）: ブロックの判断（分割、モード、MV）を、RD パスの見積もりではなく本物の
   符号化コスト（10 ビット、色差込み、実際のビット数）で行う。avmenc の cpu-used 6 と 0 の差
   （アニメ 14〜20%）の大部分はここにある。
3. 第 3 段: 候補の拡大と、足りないツールの追加。avmenc でツールを 1 つずつ外した計測
   （cpu-used 6 は 2026-10-29、cpu-used 0 は 2026-10-31〜）の結果で順番を決める。

各段は、下の「採否の判定」を満たしたものだけを `--preset max` に入れる。

## 第 1 段の設計

### (1) GOP を試して選ぶ

対象: 16 フレームのミニ GOP を取れる場面。`--preset max` は `--tune` と同じく `--bframes` の
既定を 15 にし（`--refs` 5 以上、`--qindex` 100 以上のとき）、`--gop-still` の既定を 0.5 にする
（今の 0.85 より広く候補にする。0.5 未満はアンカーの画質の上げ幅が 0 になり、16 フレームが
大きく負けた範囲なので試さない）。閾値を通ったミニ GOP を 2 通り符号化する。

- 案 1: 16 フレームのミニ GOP 1 つ
- 案 2: 8 フレームのミニ GOP 2 つ

それぞれの J = D + λ·R を比べ、小さい方を残す。

- D: 表示される 16 フレームの、元の映像との 2 乗誤差（Y + U + V、10 ビットの値で）。
- R: 16 フレーム分の出力のビット数。
- λ: RD パスと同じ重み（ビットあたり 0.025 × 量子化ステップの 2 乗。ステップは CCSO のヘッダの
  ビットに使っているものと同じ式で、そのフレームの qindex から出す）。

試し符号化は、エンコーダの状態をコピーして行う。並列 B フレームの `code_group` が使っている
状態のコピー（`Encoder::sync_from`、`CodecState::sync_refs_from`）と、`Pipeline` の参照の再構成
（`recons_`、`last_shown_`、`next_key_`）を 1 組の「試し用の状態」にまとめる。勝った方の状態を
本体に移す（または勝った方を本体でもう一度符号化する。速さを比べてどちらにするか決める。出力は
同じでなければならない）。

GPU の判定エンジンには参照ごとの `keys` で中間データを持たせている。試しの符号化で増えた
参照の `keys` は、捨てた側のものが残っても害がない（新しい鍵になるだけ）ことを確かめる。

範囲の外: 次のミニ GOP 以降への影響（アンカーが後で参照されること）は J に入れない。第 2 段以降で
後への影響を見積もれるようにしてから考える。

### (2) フレームごとのデブロックの強さを試して選ぶ

今は動画全体で 1 つの差分（`--deblock-delta`、アニメ向け設定では 0）。`--preset max` では、
フレームごとに差分を {-4, -2, 0, +2, +4} から選ぶ。

- タイルの符号化が終わった後、`end_frame` のデブロックの前に、各候補でデブロックだけをかけた
  輝度と色差の 2 乗誤差を比べ、最も小さいものを選ぶ（avmenc の picklpf と同じ考え方）。CDEF と
  CCSO の探索は、選んだ強さでデブロックした後に今どおり 1 回だけ行う。
- 差分はフレームヘッダに書く。`df_par_bits_minus2` は `--preset max` では常に 3（5 ビットの差分）。
- タイルの符号化がデブロックの差分に依存していないこと（ブロック単位の delta LF を使っていない）を
  実装の前に確かめる。

### (3) 第 1 段でしないこと

- フレームごとの qindex を試して選ぶこと。アンカーの画質は後のフレームにも効くので、その場の J で
  選ぶと粗い方を選びがちになる。
- CDEF と CCSO の探索の変更。すでにフレームごとに探索している。細かくする余地があるかだけ、
  第 1 段の計測のついでに調べる。

## 採否の判定

- 素材: 8 本以上（アニメ: AM、Dragon Maid OP、AIR OP、chika、Angel Beats OP（720p）。実写: 吉村、
  crowd_run、park_joy、ducks_take_off から 3 本以上）。かぐやはアニメの代表として参考にならない
  （利用者、2026-10-31）ので、判定には使わない。120 フレームに加え、静かな場面と動く
  場面が混ざった 600 フレームの区間（2026-10-30 の tunes の記録にある AM / AIR / Angel Beats /
  Dragon Maid の区間）。
- PSNR-Y の BD-rate（q100〜190 の 4 点、`scripts/bdrate.py`）が `--preset max` なしより
  下がること。
- VMAF NEG の BD-rate（同じ 4 点）が悪化しないこと（+0.1% 程度は誤差として扱う）。
- 比べる相手として、AV1 の最も遅い設定（libaom cpu-used 0、SVT-AV1 preset 0）を同じ素材で
  1 回符号化して保存しておく。avmenc cpu-used 0 は 33 フレームの保存済みの結果を使う。
- 速さも毎回測って記録する（1080p の 1 フレームあたりの秒数）。

## テスト

- `tests/test_cli.cpp`: `--preset max` で符号化した小さな動画（64x48、20 フレーム、静止した
  部分を含む）を avmdec で復号し、`--recon` と一致すること。
- 不正な値（`--preset fast` など）が理由つきで拒否されること。
- 試し符号化の後に本体の状態が正しいこと: 同じ入力で、GOP を試して選んだ結果と、その選択を
  固定して普通に符号化した結果が同じバイト列になること。
- GUI: チェックボックスをオンにすると `--preset max` が渡ること（`gui/tests/CommandTests.cs`）。

## 速さの見込み（1080p、推測）

| | 1 フレームあたり |
|---|---|
| 今の既定 | 0.1〜0.2 秒 |
| 第 1 段 | 0.5〜1 秒 |
| 第 1〜2 段 | 5〜20 秒 |
| 参考: avmenc cpu-used 0、1 スレッド（実測） | 2,524 秒 |

## 危険と対策

- **試し符号化の状態が本体に漏れる**: 状態のコピーを 1 か所にまとめ、上の「同じバイト列になる」
  テストで確かめる。
- **J が後のフレームへの影響を見ないので、16 フレームを選びすぎる / 選ばなすぎる**: 600 フレームの
  区間で確かめる。外れるなら、次のミニ GOP の最初のフレームまで含めて比べる。
- **VMAF がアニメに合わない**: VMAF は判定の補助にとどめ、主は PSNR。大きく食い違ったときは
  実際の映像を見て確かめる。
