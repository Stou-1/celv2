# 10-bit and HDR (plan step 5) (2026-10-29)

What had to change for 10-bit 4:2:0 input and HDR signalling, found by reading `src/` and AVM's
decoder, and what was built (branch feat/10bit, "Built" at the end).

## Where 8 bits is assumed

| Place | Today | Change |
|---|---|---|
| `io/y4m` | `Frame420` holds `uint8_t` planes; the reader rejects anything but 8-bit `C420` (and its jpeg / mpeg2 / paldv siting tags) | Parse `C420p10` (16-bit little-endian samples). One sample type for every frame: `uint16_t` planes plus `bit_depth` (see below). |
| `bitstream/seq_header` | `bit_depth = AVM_BITS_8`; writes bit-depth LUT index 1 (10 → 0, 8 → 1, 12 → 2) | Take `SeqConfig::bit_depth`; profile `MAIN_420_10_IP0` already covers 10-bit. |
| `core/quant`, `core/rd_pass`, `core/encoder` | `av2_{dc,ac}_quant_QTX(..., AVM_BITS_8)`; dequant clamp with `bd = 8` (14 places) | Pass the sequence's bit depth. Steps grow 4x at 10-bit, so everything already weighed in squared steps (TCQ, `quantize_cost`, `kTcqBitWeight`) carries over unchanged. |
| Pixel-domain RD weights | `kRdBitWeight` (block_writer: SSE per bit), CCSO's `sse_per_bit`, CDEF search, `dropped_cost` | SSE grows 16x at 10-bit: scale the per-bit weights by `1 << 2 (bd - 8)`, or compute SSE on `>> (bd - 8)`. One helper, used everywhere. |
| `state/codec_state` | Copies 8-bit source into AVM's frame buffers, which are already `uint16_t` | Copy without widening; set `buf.bit_depth`, `xd->bd`. AVM's own code is high-bit-depth throughout (`*_highbd_*`), so prediction, transforms, loop filters, CDEF, CCSO need no change. |
| GPU / CPU engines | `Plane` of `uint8_t`; SAD/SATD costs in 8-bit units | Keep the decision input 8-bit: the engines get `source >> (bd - 8)` (and the 8-bit reconstructions). Candidates are a shortlist; the CPU RD pass and the coder decide on full precision. Halves GPU memory and bandwidth at 16K. |
| `verify/avm_decode` | Throws unless AVM outputs 8-bit | Accept the stream's depth; compare 16-bit samples. |
| `main.cpp` / GUI | No depth option | Depth from the y4m header; `--bit-depth 8|10` to force (10-bit from 8-bit input is a real gain for banding; worth one BD check). |

Memory: `uint16_t` everywhere doubles frame memory (16K 4:2:0: 200 → 400 MB a frame). The DPB holds
up to 16 reconstructions, so 16K at 10-bit needs ~6.5 GB of host memory; fine on this machine, note
it in the README.

## HDR signalling (AV2 v1.0.0, from AVM's decoder)

- Colour description is not in the sequence header: it is in `OBU_CONTENT_INTERPRETATION`
  (`av2_read_color_info`, obu.c). `color_description_idc` (Rice-Golomb k=2): 1 = BT.709 SDR,
  2 = BT.2100 PQ, 3 = BT.2100 HLG, 0 = explicit primaries / transfer / matrix (8 bits each); then
  `full_range_flag`.
- HDR10 static metadata: metadata OBUs `OBU_METADATA_TYPE_HDR_MDCV` (mastering display) and
  `OBU_METADATA_TYPE_HDR_CLL` (MaxCLL / MaxFALL), once per key frame.
- Input: y4m has no colour tags beyond `XCOLORRANGE`; take `--colour pq|hlg|709` and
  `--mdcv` / `--cll` on the command line (the GUI reads them with ffprobe, which it already runs).

## Test material

- `SolLevante_HDR10_r2020_ST2084_UHD_24fps_1000nit.mov` (CC BY 4.0): 3840x2160,
  12-bit 4:4:4, PQ, BT.2020. Convert with ffmpeg to `yuv420p10le` y4m. Its SDR grade (10-bit 4:2:2)
  is the same content for an SDR 10-bit check.
- The existing 8-bit sources, coded at 10-bit, for the "8-bit in, 10-bit coding" check.
- PSNR at 10 bits: peak 1023; `psnr3.py` needs the depth. AV1 comparison: aomenc `--bit-depth=10`.

## Order

1. `Frame420` → `uint16_t` + `bit_depth`, 8-bit input widened at read; output byte-identical to
   today at 8 bits (the guard: `test_ippp` plus a 1080p cmp).
2. Bit depth through seq header, quant and the RD weights; y4m 10-bit; AVM decode check at 10-bit.
3. Content interpretation OBU and HDR metadata OBUs; check with avmdec and ffprobe.
4. BD at 10-bit against aomenc 10-bit (Sol Levante HDR, plus one 8-bit source at 10-bit).

## Built (2026-10-29)

- One correction to the table above: AV2 has one quantizer table for every depth. A 10-bit frame
  codes qindex + 48 (24 qindex double the step) in 9 bits, up to 303, so the steps do not grow 4x
  at the same qindex. `--qindex` keeps the 8-bit scale; `SeqConfig::coded_qindex()` adds the 48.
- `Frame420` keeps the full-depth samples in `hy / hu / hv`; `y / u / v` hold them rounded to 8 bits
  for the decisions (engines, RD pass, scene cuts, global motion), as planned.
- The coder's residuals, SATD and the CDEF and CCSO searches read the full-depth source. CCSO
  follows ccso.c: bands from the luma shifted down to `max_band_log2` bits, edge thresholds and
  offsets in the depth's own units.
- `--bit-depth 8|10`, 10 by default: 8-bit sources code better at 10 bits. 33 frames 1080p
  q100-190, BD-rate of 10 against 8 bits: anime A Y -20.1%, anime C -12.5%, anime B -4.3%, live
  action -7.7% (U / V -13%), at the same speed. Anime D's 30 frames are near-flat (PSNR 58-71 dB) and
  gave no reliable number.
- `--colour 709|pq|hlg`, `--range`, `--mdcv`, `--cll`: the content interpretation OBU and the HDR10
  metadata OBUs (OBU_METADATA_SHORT) after the sequence header of every keyframe. The MDCV payload
  takes the primaries in R, G, B order (AV1's layout; AVM stores the payload without reading it).
- AVM decodes 10-bit and HDR-signalled streams equal to `--recon`; the 8-bit output is unchanged.

GUI (branch feat/gui-hdr): codes at 10 bits (`OutputFormat.BitDepth`, saved as `CodedBitDepth` so
presets from the 8-bit-only days load as 10). Sources above 8 bits reach celv2enc as `yuv420p10le`
y4m (ffmpeg needs `-strict -1` for it); HDR (PQ / HLG) is no longer tone-mapped: `--colour pq|hlg`,
`--range full` for full-range sources, and `--mdcv` / `--cll` from the first frame's side data
(`ffprobe -show_frames -read_intervals %+#1`: x265 puts them in SEI, so stream side data is
empty). The MP4 `colr` box says BT.2020 / PQ or HLG. An 8-bit setting still tone-maps to SDR.
av2_mux writes no `mdcv` / `clli` boxes; the metadata is in the AV2 stream only.
