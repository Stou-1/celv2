# The 48-thread fps cap (2026-11-09)

The C17 step 0b report found S1 capped near 9.6 fps at 48 threads, with RD-pass CPU savings not showing in fps.
This note finds where the cap is. Build 90ec138 plus the frame wall times below (`CELV2_PROFILE=1`); RTX 5090, Xeon
658X (24 cores, 48 threads); `--refs 7 --qindex 130 --tune animation --device vulkan`; S1 = mxam600.y4m.

## Verdict

1. **The 9.6 fps is the bench clip's chunk count.** S1's first 240 frames are two scene chunks, so only two of
   the three workers ever run. The full 600 frames (6 chunks) run at **12.4 fps** with the same build.
2. **At three workers the 24 cores are nearly full, though only 55% of the 48 threads are busy.** One thread per
   core (affinity 0x555555555555) gives 11.4 fps against 12.4 on all 48: hyper-threading adds 8%. The same work
   reads 30% more CPU time with both threads of a core busy (1539 against 2205 ms a frame).
3. **Each worker is bound by one frame's chain of steps**, and more workers make every chain longer: 6 workers run
   11.0 fps (the C24 row in tried-not-kept says the same for 4 and 5).
4. **The RD pass is a quarter of that chain**, so a CPU saving in it shows in fps at about a fifth of its size: the
   memo (-15% CPU) is +2.7% fps here, and C17 step 1 (-8.5% CPU, estimate) would be about +2% at 48 threads.
   On 8-16 threads, where the cores are the limit, it is worth about +9% (the step 0b report).

At three workers a reference frame takes about 230 ms:
- 35 ms waiting for the GPU's first row;
- 56 ms of RD pass after it;
- about 50 ms of coding after the RD pass is done;
- about 52 ms of in-loop filters (280 ms of CPU on about 5 threads);
- 9 ms of global motion.

## What moves fps at 48 threads

- **The filters' wall time.** They are 23% of the chain and run on about 5 threads. Turning them off is +20%.
  Filtering rows as the coder finishes them, or a wider split, could take half of that (estimate: +8-10% fps,
  same bytes). A new speed item.
- **The coder after the RD pass** (about 50 ms). Four tiles take 14 ms off it for a byte change.
- **The GPU's wait** (35 ms at 3 workers). Its own queue per engine halves it without moving fps (the C24 / queues
  rows in tried-not-kept), so it is not what limits on its own.
- CPU savings in the RD pass: about a fifth of their size at 48 threads, nearly all of it on 8-16 threads.

Tried and dropped here: coding the rows on their own threads instead of the shared pool (the rows sleep on the RD
pass and could hold the pool's threads). Same bytes, 11.60 fps against 12.06-12.43: slower.

## Reproduce

```bash
CELV2_PROFILE=1 celv2enc -i sources/mxam600.y4m -o s1.ivf --workers 3 --refs 7 --qindex 130 --tune animation --device vulkan
```

The frame wall line is `celv2enc: profile: frame wall`. The bytes are unchanged: s1cut b6a5bc01 on Vulkan with
`--workers auto` and on `--device cpu --workers 1`; S1 600 2281490e.
