# 計画と違った結果への回答（実装担当へ、2026-11-05）

docs/reports/2026-11-05-plan-differences.md の「設計担当に決めてほしいこと」への回答。ユーザーの了承を得て、設計書を更新した。設計書が基準で、ここは入口。

## 最初にすること：MHCCP の読み取りの確認

be63bcf は症状を止めただけで、読んでいる箇所は未特定。**符号化器が書いていない輝度を読んでいるなら、デコーダーと結果が食い違うおそれがある。** これは推測で、まだ確かめていない。リリースの前に、次の順で確かめる。

1. 報告にある再現の素材（ソースの 170〜260 フレーム、2 つ目のチャンクの先頭のキーフレーム）と S1 を AVM でデコードし、`--recon` と比べる。be63bcf の前と後の両方。
2. 新しいフレームの輝度を、定数ではなく乱数で埋める（種を変えて 2 通り）。バイト列が変われば、いまも未書き込みの領域を読んでいる。
   - 0 と 0xFFFF で同じになったので、定数では見分けられない。定数の足し算に影響されない計算（平均を引く、差を取る）が読んでいる可能性がある。
3. 読んでいる箇所を見つけ、`shortcut:` のクリアを外す。再現する素材を、テストに使える大きさまで切り詰める。

1 で不一致が出たら、ほかの作業より先に直し、ユーザーに報告する。

## 16K の VRAM

- 半画素の 4 面（報告書の B）を Vulkan の既定にする。足りなければ A、それでも足りなければ CPU エンジン。C と D はやめる。
- 既定にする前に、S1 と S3 を両方の GPU で計る。計測が 16K だけなので。全体が 1% を超えて遅くなるなら、フレームの大きさで 16 面を残す。
- 報告書の 9 フレームでは、参照は約 5.6 枚分だった。7 枚持つ長い 16K の素材で VRAM を測り直す。面以外の約 4.6 GB の内訳も出す。

設計書：2026-11-04-speed-budget-design.md、docs/design/pipeline-map.md。

## おすすめの順

1. MHCCP の確認
2. 4 面の既定（S1、S3 の計測から）
3. 速さの財源づくりの段階 A。量子化と順変換が CPU 時間の 55〜76%。帳簿の「補った分」はまだ空で、以下はこの帳簿を使う
4. `--warp` 段階 A2
5. `--screen` の RD パス（戻り道）と既定の条件

AV1 との差の内訳が完成したら、一覧を設計担当に渡す。上の順より大きな候補が出れば、そちらを優先する。
