# 16K の VRAM と、1/4 画素の面の持ち方（選択肢 A〜D）（2026-11-04）

速さの財源づくりの設計書（docs/superpowers/specs/2026-11-04-speed-budget-design.md）が「16K の実測の後に書く」とした、エンジンの VRAM を減らす設計の材料。

## 結論

- いまの作り（参照ごとに 1/4 画素の 16 面）の 16K での VRAM の最大使用量：RTX 5090 16.48 GB、Arc Pro B50 14.54 GB（16 GB のほぼ全部）。設計書の見積もり約 15 GB に近い。
- **選択肢 B（半画素の 4 面だけ持ち、残りは読むときに補間）が、VRAM・時間とも良い**：VRAM 7.6 GB（−54%）、RTX 5090 の判定エンジン −7%（1172 → 1086 ms/frame）、B50 の符号化全体 −15%（21.0 → 17.8 s/frame）。B50 の判定エンジンだけなら +10%（8052 → 8893 ms）。
- 選択肢 A（面を持たない）は VRAM 5.4 GB（−67%）だが、判定エンジンが 5090 で +9%、B50 で +28%。
- 選択肢 C（近い 2 枚だけ 16 面）は VRAM 9.3 GB、B50 の判定エンジン +21%（参照 4 枚）。D（行の周りの帯）は VRAM 5.6 GB、B50 の判定エンジン +67%（同）。どちらも B に及ばない（下の「C と D」）。
- どの持ち方でも、同じ判断（同じバイト列）。RTX 5090・B50 とも確認（test_cli `cli_vk_phase_layouts`、吉村 12 フレームの符号化）。

## 計測

- 素材：a16k（15360x8640、9 フレーム）。
- VRAM：`celv2enc --refs 7 --qindex 130 --device vulkan|vulkan2` の全体の符号化を、Windows の性能カウンター「GPU Process Memory(pid_*)\Dedicated Usage」で 0.5 秒ごとに読み、その最大。
- 判定エンジンの時間：tools/engine_bench（エンジンだけ、参照 2 枚、4 フレーム目以降の平均）。
- 切り替え：`CELV2_VK_PHASES=A|B`（計測用の環境変数。既定は 16 面のまま）。

| 持ち方 | VRAM 最大 5090 / B50 | 符号化 5090 / B50 | 判定エンジン 5090 / B50 |
|---|---|---|---|
| 16 面（いま） | 16.48 / 14.54 GB | 5.4 / 21.0 s/frame | 1172 / 8052 ms |
| A：面を持たない | 5.36 / 5.38 GB | 5.5 / 20.7 s/frame | 1277 / 10335 ms |
| B：半画素の 4 面 | 7.59 / 7.61 GB | 5.4 / 17.8 s/frame | 1086 / 8893 ms |

- 同じ実行での CUDA エンジンの時間（持ち方の切り替えは Vulkan だけ）：1092 / 1180 / 1083 ms。測るたびのばらつきは ±8% ほどある。
- B50 の 16 面は VRAM がほぼいっぱいで、符号化全体が遅かった（14.54 GB）。B で余裕ができ、符号化全体が速くなったと見ている。

## 作り（計測用）

- `common.slang` の `Plane::at_q()`：`phase` の上位ビットで持ち方を表す。A は 1/4 画素の位置を読むたびに `subpel_px()` で補間、B は半画素（(qy, qx) が偶数）の 3 面と元の面の 4 面だけ持ち、残りを補間。補間した値は、あらかじめ作った面の値と同じ（端の扱いも同じ）。
- `subpel.slang`：B では半画素の 3 面（位相 2、8、10）だけ作る。

## C と D（2026-11-04 午後に実装して計測、bd2edea）

- **C（近い参照 2 枚だけ 16 面、残りは A）**：16 面の置き場を 2 つ持ち、その起動で一番近い 2 枚の参照を参照の番号で入れておく。ほかの参照は読むたびに補間。
- **D（処理中の超ブロック行の周りだけ面を持つ）**：参照ごとに、1 面のあとに「超ブロック 1 行 ＋ 上下 64 行」分の位相 1〜15 の帯を持ち、各行の前に作り直す。帯の外と、動き探索の 1/4 画素の詰め（行より前にフレーム全体で走る）は補間。
- どちらも同じバイト列（a16k の全体の符号化 9 フレームで 5 通りとも MD5 83E9AE1D、5090・B50 とも。小さい素材と吉村 1080p `--refs 7` でも一致。D は上下 0 行でも一致）。

| 持ち方 | VRAM 最大 5090 / B50 | 符号化 5090 / B50 | 判定エンジン B50、参照 2 / 4 枚 |
|---|---|---|---|
| 16 面（いま） | 16.48 / 14.55 GB | 10.8 / 24.8 s/frame | 8211 / 12848 ms |
| A：面を持たない | 5.36 / 5.39 GB | 10.7 / 23.8 s/frame | 10641（+30%） / 16918（+32%） |
| B：半画素の 4 面 | 7.59 / 7.61 GB | 10.8 / 20.9 s/frame | 9167（+12%） / 14381（+12%） |
| C：近い 2 枚だけ 16 面 | 9.32 / 9.35 GB | 10.5 / 21.8 s/frame | 8603（+5%） / 15555（+21%） |
| D：行の周りの帯 | 5.61 / 5.63 GB | 9.5 / 26.9 s/frame | 12456（+52%） / 21419（+67%） |

- 午後の計測は、AV1 との比較（avmenc 約 50 本）が CPU を埋めている中で行った。符号化全体の時間は朝の値（5.4 / 21.0 s/frame）より遅く、持ち方どうしの比較だけに使える。
- 判定エンジンの時間は tools/engine_bench（参照の枚数を指定できるようにした）。RTX 5090 の値は、持ち方に関係しない CUDA エンジンの時間が同じ実行の中で 1067〜1709 ms とばらついたので、表に入れていない（CPU が空いたときに測り直す）。B50 は GPU の時間が大半で、朝の A・B の値（+28%、+10%）と合う。
- **C** は、参照 2 枚なら 16 面と同じ作りなので速いが、参照 4 枚では B より遅く、VRAM も B より多い。近い 2 枚が起動ごとに入れ替わり、そのたびに 16 面を作り直すため。
- **D** は VRAM が A に近い（帯の分 +0.25 GB）が、一番遅い。行ごとに参照の数だけ帯を作り直し、帯は上下に重なるので、フレーム全体の面を作るより約 3 倍の計算になる。行の順に帯をずらして作り足す形にすれば減らせるが、行を並べて流す（row streams）ときは行が飛ぶので効きにくい。

## 設計側への提案

- B を既定にする（VRAM の予算に関係なく）のが良さそう。5090 で速くなり、B50 では符号化全体が速くなる。C・D を測った後も変わらない：C は VRAM・時間とも B に負け、D は VRAM で B に勝つが時間で大きく負ける。
- 判定エンジンだけの時間で B50 が +10% になる分は、設計書の段階 C（Vulkan エンジンの改善）で取り返す対象。
- A は VRAM がもっと足りない GPU（8 GB 級）向けの予備。

## 全体の速さの確認と、決めた規則（2026-11-05）

設計書の「4 面を既定にする前に、S1 と S3 を両方の GPU で計る」の結果。**全体が 1% を超えて遅くなったので、設計書の分岐どおり、小さいフレームは 16 面のままにした。** どの持ち方でも同じバイト列。gap33（avmenc 6 本）の負荷の中で、16 面と 4 面を交互に計った。

| 素材 | RTX 5090 16 面 / 4 面 | Arc Pro B50 16 面 / 4 面 |
|---|---|---|
| S1（1080p） | 9.44 / 5.42 fps（−43%） | 1.40 / 0.78 fps（−45%） |
| S3（4K） | 2.09 / 1.80 fps（−14%） | 0.42 / 0.26 fps（−38%） |
| 8K（9 フレーム） | 1.90 / 1.95 s/frame（+2%） | 4.6 / 5.4 s/frame（+17%） |
| a16k（9 フレーム） | 7.3 / 7.1 s/frame | 23.1 / 19.4 s/frame（−16%） |

- S1、S3 の 5090 は 3 回の平均（4 面は 5.04〜5.65 fps、1.71〜1.97 fps と揺れる）、B50 は 1 回。8K と 16K は 2 回の平均。差が大きいので、負荷のせいではない。
- 判定エンジンだけの時間（16K）では +10% ほどでも、1080p では全体の律速が判定エンジンに移るので、全体が大きく落ちる。

**規則（`vk_phase_layout()`）：** 8192 x 8192 画素未満は 16 面、それ以上は 4 面。空き VRAM に入らなければ 4 面、面なし（A）の順に落とし、それでも入らなければ `--device auto` は CPU エンジン、明示の `--device vulkan` はエラー。必要な量は、参照 7 枚分の面と、その他 1 画素 35 バイト（16K の 4.6 GB から）の見積もり。8K と 16K の間は計っていない。

C と D は消した（tried-not-kept に記録）。`CELV2_VK_PHASES` は A、B、16 をテスト用に残した。

**まだ計っていないもの（設計書の残り）：** 参照 7 枚を持つ長い 16K の素材の VRAM（両方の GPU）、その他 4.6 GB の内訳、静かな CPU での 5090 の判定エンジンの時間。→ 下の「残りの計測」で計った。

## 残りの計測（2026-11-07、静かな機械）

### 参照 7 枚の 16K の VRAM

素材 a16k33（a16k の 9 フレームを往復させて 33 フレームにしたもの、6.57 GB）、`--refs 7 --qindex 130`、132afe4 の build。VRAM は前と同じ読み方（Dedicated Usage の最大、GiB）。

| 持ち方 | VRAM 最大 5090 / B50 | 符号化 5090 / B50 |
|---|---|---|
| 既定（16K は B：半画素の 4 面） | 8.15 / 8.20 GiB | 5.9 / 36.4 s/frame |
| 16 面（`CELV2_VK_PHASES=16`） | 18.53 / 12.67 GiB | 5.7 / 122.1 s/frame |

- どちらの GPU、どちらの持ち方でも同じバイト列（MD5 D6CBD99B）。
- 既定の 8.15 GiB は 9 フレームの 7.59 GiB から +0.56 GiB：参照が 6 枚から 7 枚になった分（4 面 1 枚 0.49 GiB と縮小の段）。
- 16 面は B50（16 GB）に入らない。12.67 GiB で止まり、残りは共有メモリーに逃げて、符号化が 3.4 倍遅い。既定の規則（8192 x 8192 以上は 4 面）なら起きない。
- 5090 では 16 面のほうが符号化全体で 3% 速い（5.7 / 5.9 s/frame、1 回ずつ）。VRAM に余裕がある GPU では、16K でも 16 面を選ぶ余地がある（下の「設計側への提案（2026-11-07）」）。
- 規則の見積もり（参照 7 枚の面 ＋ その他 1 画素 35 バイト）は 8.36 GB = 7.79 GiB で、実測 8.15 GiB より 4% 少ない。その他の実測は 1 画素 38 バイト（次の節）。

### その他の内訳

`vkAllocateMemory` の大きさを一時的に書き出して（コミットしていない）、a16k 9 フレーム、`--refs 7`、5090 で数えた。参照 7 枚のときの値に直してある（n = 1 面 132.7 MB）。

| 中身 | 大きさ | 1 画素あたり |
|---|---|---|
| 参照の 1/4 画素の面（B：4 面 x 7 枚） | 3.46 GiB | 28 バイト |
| **イントラの費用（`Src::intra`、超ブロックごとに 425 ブロック x 13 モード x int64、2 つ）** | **2.67 GiB** | **21.6 バイト** |
| **判定の出力（`out`、`SbOut` 38,872 バイト x 32,400 超ブロック、フレーム全体）** | **1.17 GiB** | **9.5 バイト** |
| 縮小の段（参照 7 枚と元の 2 枚、1/2〜1/32） | 0.37 GiB | 3.0 バイト |
| 元のフレームの面（2 つ） | 0.25 GiB | 2.0 バイト |
| 動きベクトル（参照 7 枚 x 5 段 x 2） | 0.14 GiB | 1.2 バイト |
| 費用の行（`costs`、1 行分） | 0.06 GiB | 0.4 バイト |
| 合計 | 8.12 GiB | 65.7 バイト |

- 合計は実測の最大 8.15 GiB と 0.03 GiB の差。その他（参照の面を除く）は 4.66 GiB、1 画素 38 バイト。
- 大きいのはイントラの費用と判定の出力で、その他の 82%。
- 減らす候補（設計の判断に回す、どれも同じバイト列のまま作れるはず）：
  - イントラの費用を int32 に：−1.33 GiB。費用の上限が int32 に入るかの確認が要る。
  - 判定の出力を、行の数だけ持つ代わりに、流している行の分の輪にする：−1.1 GiB ほど。行を並べて流す（row streams）ときの数だけ要る。
  - 元の 2 つ（`prepare()` が次のフレームを先に作る分）のイントラの費用は、2 つ目を持たなければ −1.33 GiB だが、先に作る速さを失う。

### 判定エンジンの時間（A〜D）

`engine_bench`（a16k 9 フレーム、qindex 130、4 フレーム目以降の平均）。C と D は消してあるので、bd2edea の engine_bench を別の作業フォルダーでビルドして計った。132afe4 の列は今の build（A、B、16 面のみ）。静かな機械、1 回ずつ。

| 持ち方 | 5090 参照 2 / 4 枚（bd2edea） | 5090 参照 2 / 4 枚（132afe4） | B50 参照 2 / 4 枚（bd2edea） | B50 参照 2 / 4 枚（132afe4） |
|---|---|---|---|---|
| 16 面 | 769 / （6756）ms | 731 / 860 ms | 11049 / 16784 ms | 11852 / 18459 ms |
| A：面を持たない | 1134 / 1713 | 822 / 1584 | 14258 / 23877 | 15505 / 24825 |
| B：半画素の 4 面 | 817 / 1584 | 728 / 1304 | 11992 / 19762 | 12712 / 21297 |
| C：近い 2 枚だけ 16 面 | 723 / 1446 | — | 10947 / 21242 | — |
| D：行の周りの帯 | 966 / 1665 | — | 15428 / 27668 | — |

- bd2edea の engine_bench は同じ実行で CUDA エンジンも作る。5090 の 16 面・参照 4 枚の 6756 ms は、CUDA の分と合わせて VRAM からあふれた値と見て、比較から外した（132afe4 の 860 ms が CUDA なしの同じ条件）。
- 5090 の参照 4 枚で B は 16 面より +52%（132afe4）。それでも参照 7 枚の符号化全体では +3%（上の表）：判定エンジンは CPU の仕事と重なって動くため。
- B50 は前の計測（+10〜15%）と同じ傾向。C は参照 4 枚で B50 では B より遅く、5090 では B より 9% 速い。VRAM は参照 7 枚で B より約 1.1 GiB 多い（16 面 2 枚と 1 面 5 枚、B は 4 面 7 枚）。前の結論（B を既定、C・D は持たない）は変わらない。

## 設計側への提案（2026-11-07）

- 規則のその他を 1 画素 35 バイトから 38 バイトに：見積もりが実測より少ないと、空き VRAM の境目で入らない持ち方を選び、共有メモリーに逃げて遅くなる（B50 の 16 面の 3.4 倍）。
- VRAM が足りる GPU（5090 の 32 GB）では、16K も 16 面にする：符号化全体で 3% 速い（1 回ずつの計測なので、決める前に測り直す）。今の規則は「8192 x 8192 以上は 4 面」で、空き VRAM を見ていない。
- VRAM の大きな使い道は、参照の面の次がイントラの費用（2.67 GiB）と判定の出力（1.17 GiB）。8 GB 級の GPU で 16K を通すなら、ここを減らすのが先。

## 設計側の判断（2026-11-07）

1. **その他を 1 画素 38 バイトに：採る。** `vk_phase_layout()` の `kOtherPerPixel` を 35 から 38 にし、上のコメントに「その他 4.66 GiB、1 画素 38 バイト（参照 7 枚、2026-11-07）」と書く。参照 7 枚の 16K で、見積もりは 16 面 18.5 GiB、B 8.15 GiB になり、実測と合う。選ぶ持ち方は 5090・B50 とも変わらない（境目にある GPU だけが変わる）。テストは今の `vk_phase_layout` のもので足りる。数字が変わる箇所だけ直す。
2. **VRAM が足りれば 16K も 16 面に：採らない。** 5090 の 16K で、16 面と 4 面の差は 2 回とも 3% だが、向きが逆。11-05 は 7.3 / 7.1 s/frame で 4 面が速く（負荷の中、2 回の平均）、11-07 は 5.7 / 5.9 で 16 面が速い（静か、1 回ずつ）。どちらもばらつき（±8%）の中なので、速さは同じと見る。16 面は VRAM を 10 GiB 多く使う。目標サイズの 2 パスや GOP 試行でエンジンが 2 つになると、どのみち入らない（空き VRAM を 2 で割る）。測り直しは要らない。見直すのは、16K を 3 回交互に測って 16 面が 2% 以上速いと出たとき。
3. **イントラの費用を int32 に、判定の出力を輪に：今は作らない。** 8 GB 級の GPU は手元になく、効果を確かめられない。今でも 8 GB 級の 16K は A で動く（7 枚 x 1 面 + 38 バイトで 1 画素 45 バイト、6.0 GB）。2 つとも作ると B が 1 画素約 46 バイト（6.1 GB）になり、8 GB に入る。得は A から B への分で、B50 の符号化全体なら −14%（20.7 → 17.8 s/frame、11-04）。イントラの費用は GPU の中だけで使い（`finalize`）、CPU へは戻らない。なので 1080p の速さは変わらない。作るのは、8 GB 級の GPU が試験機に入ったとき、または 8 GB で 16K を使う人が出たとき。int32 は、その前に費用の上限が int32 に入ることを確かめる。
