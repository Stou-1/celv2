# 行ごとに進む GPU 判定: 計測（2026-10-25）

## 結論

- **出力は変わらない**。720p と 1080p、1タイルと2タイルの4組とも、変更前と変更後の IVF の MD5 が一致した（下の「出力の一致」）。
- **1枚あたりの時間（定常状態の P フレーム）**: 720p 2タイルで **10.95 → 9.10 ms（−17%）**、1080p 2タイルで 20.76 → 16.03 ms（−23%）、720p 1タイルで 13.57 → 12.56 ms（−7%）。
- **目標の 12 ms 以下（720p、2タイル）は満たした**（9.10 ms）。ただし設計時の「約 20 ms」は DCT/量子化の高速化より前の値で、変更前の main もすでに 10.95 ms だった。この変更で減ったのは 1.85 ms。
- **GPU の判定はほぼ完全に隠れた**。720p 2タイルでは GPU が 2.63 ms で全行を終え、遅いほうのタイルの符号化は 7.31 ms まで続く。その間にタイルスレッドが `wait_row` で待つ時間は、律速するタイルで 1枚あたり 0.04 ms だった。
- **残っている待ちはすべて CPU 側**。大きい順に、遅いタイルの符号化 6.16 ms（タイル間の差 1.9 ms）、`end_frame` の復元画像のコピー 1.0 ms、`launch` の CPU 部分 0.66 ms、タイル出力バッファのゼロ埋め 0.60 ms。
- **分割決定の2本目のストリームは不要**。行間の隙間と `finalize_kernel` を合わせても 1枚 0.22 ms（720p）で、それも全部 CPU の符号化の陰にある。
- **`speed:` 行の fps は変更前後で直接比べられない**。変更前は CUDA の初期化（約 95 ms）が計測区間に入り、変更後は `GpuEngine` のコンストラクタ（計測区間の外）に移った。初期化を除くと、720p 2タイルで 87.6 → 106.8 fps（+22%）。

## 行ごとの GPU の時間（変更後、中央値）

| 項目 | 720p（12行、K = 16） | 1080p（17行、K = 12） |
|---|---|---|
| `cost_kernel`（1行） | 80 µs | 111 µs |
| `finalize_kernel`（1行） | 12 µs | 12 µs |
| `cost_kernel` の終わり → `finalize_kernel` の始まり | 2.3 µs | 2.3 µs |
| `finalize_kernel` の終わり → 次の行の `cost_kernel` の始まり | 6.4 µs | 6.5 µs |
| 1行の結果の転送（GPU → 固定メモリ） | 1.3 µs | 1.8 µs |
| 1枚の合計: cost / finalize / 隙間（上の2つの和） | 0.97 / 0.15 / 0.10 ms | 1.89 / 0.23 / 0.14 ms |
| 行ごとの判定の全体（動き探索の終わり → GPU の終わり） | 1.23 ms | 2.47 ms |
| 参考: 変更前の `decision_kernel`（フレーム全体で1回） | 1.45 ms | 3.09 ms |

まれに `finalize_kernel` が 0.2〜0.9 ms、隙間が 0.3〜0.4 ms になる行がある（1回に数行）。クロックの変化か GPU の割り込みとみられ、どの行と決まってはいない。

## 残っている待ち（720p 2タイル、律速の順、1枚 9.23 ms の内訳）

1. **遅いタイルの符号化 6.16 ms**。タイル0 は 4.26 ms、タイル1 は 6.16 ms で、差の 1.9 ms はタイル0 のスレッドが遊んでいる。1080p も 8.31 対 11.30 ms。右半分のほうが重い素材なので、タイルを増やす（`--tile-columns 2`）か、タイル内を並列にしないと縮まらない。
2. **`end_frame` 1.01 ms**（1080p 2.12 ms）。ほぼ全部が復元画像の 16 ビット → 8 ビットのコピーと端の拡張（`ef_recon` 0.95 ms）。1スレッドで、全タイルの後に直列に走る。
3. **`launch` の CPU 部分 0.66 ms**（1080p 0.90 ms）。原画と参照の固定メモリへの `memcpy` と、カーネルの起動 31 回、転送 14 回、イベントの記録 12 回。タイルスレッドはこの後でしか始まらない。
4. **タイル出力バッファのゼロ埋め 0.60 ms**（1080p 1.24 ms、1タイルの 720p 1.06 ms）。毎フレーム `out[t].buf.resize(pels * 4 + 4096)` で新しく確保してゼロで埋めている（`begin_tile` 自体は 0.01 ms）。ただし 720p 2タイルでは、これを無くしても最初の SB は 0行目の公開（1.53 ms）を待つので、律速するタイルで縮むのは約 0.06 ms だけ。1080p では約 0.7 ms、720p 1タイルでは約 0.3 ms 縮む見込み。
5. スレッドの起動と `begin_frame` 0.34 ms、組み立てと IVF 0.21 ms、join 0.15 ms、`wait_row` 0.10 ms。

GPU 側でいちばん長いのは、フレーム全体で1回の動き探索（アップロードを含めて 0行目の公開まで 1.53 ms）。いまは 3 と 4 の陰にあるが、3 と 4 を縮めると、次はこれがクリティカルパスに出てくる（範囲外とした「動き探索の行単位化」）。

## 気づいたこと

1. **1タイルでは、GPU と重ねるとタイルの符号化自体が遅くなる**。720p 1タイルで 8.57 → 9.46 ms（3回の中央値、+0.9 ms）、出力バッファのゼロ埋めも 0.80 → 1.06 ms。2タイルではタイル1 が 5.73 → 6.15 ms（+0.4 ms）、1080p ははっきりしない（11.44 → 10.77 ms）。回収スレッドが `cudaEventSynchronize` で CPU を回し続けているせいかと考え、`cudaEventBlockingSync` を付けた版を一時的に作って計ったが、変わらなかった（9.68 ms、1枚の時間は 12.87 ms でむしろ少し遅い）。原因はわかっていない。
2. **最初の P フレームが遅い**（720p 2タイルで 17.7 ms、変更前も 19.2 ms）。動き探索のカーネルが初めて動く枚。定常状態の数字には入れていない。
3. **設計時の「約 20 ms」は古い**。DCT/量子化の高速化の後、変更前の main は 720p 2タイルで 10.95 ms で、そのうち GPU の判定（起動と完了待ち）は約 3.1 ms だった。`decision_kernel` も、設計時の約 4.8 ms に対して今は 1.45 ms と計れた。

## 2本目のストリーム（範囲外の候補）について

**今はやる価値がない**。2本目のストリームで縮められるのは、`finalize_kernel` と行の間の隙間で、1枚あたり 0.22 ms（720p）、0.37 ms（1080p）。GPU は遅いタイルが終わる 4.7 ms（720p）前に全行を終えていて、律速するタイルの `wait_row` は 0.04〜0.07 ms しかない。縮めても、隠れている GPU の時間が短くなるだけで、1枚の時間は変わらない。

## 次の一手

1. `end_frame` の復元画像のコピーをタイルスレッドに分ける（1枚 −1.0 ms、1080p −2.1 ms の上限）。
2. `launch` の CPU 部分を減らす（原画を読み込み時に固定メモリへ置くなど）。上限は 1枚 −0.66 ms。
3. タイル出力バッファをフレーム間で使い回す。1080p で −0.7 ms。720p 2タイルでは動き探索の待ちに置き換わるだけ。
4. 1タイルで符号化が遅くなる原因（気づいたこと1）を調べる。
