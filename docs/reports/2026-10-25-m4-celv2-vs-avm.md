# M4 比較レポート: celv2enc と AVM avmenc（2026-10-25）

## 結論

- **速度**: CelV2 は AVM（`--good --cpu-used=6`, 1スレッド）より **約300倍速い**（実時間比 0.0033 / 0.0031）。
- **圧縮効率**: 同じ PSNR-Y を出すのに、CelV2 は AVM より **720p で +227.5%、1080p で +106.6%** 多くのビットを使う（BD-rate）。
- **正しさ**: CelV2 の復元画像は、AVM デコーダ（プロセス内の検証用デコーダと外部の `avmdec.exe` の両方）の出力とビット単位で一致する（Task 10 のメモ、テスト 13/13）。

## 計測条件

| 項目 | 内容 |
|---|---|
| 素材 | `bench.y4m`（1280x720, 30fps）、`src1080.mp4` の先頭30枚を y4m にしたもの（1920x1080, 30fps） |
| 枚数・構成 | 各30枚、IPPP（最初の1枚だけ KEY） |
| CelV2 | `celv2enc -i src -o out.ivf --qindex Q --frames 30`（RTX 5090、CUDA 13.3） |
| AVM | `avmenc --ivf --good --cpu-used=6 --end-usage=q --qp=Q --threads=1 --lag-in-frames=0 --limit=30` |
| Q | 120, 150, 180, 210 |
| PSNR-Y | `avmdec --i420` で復号し、ffmpeg の psnr フィルタで原画と比較（30枚の平均） |
| BD-rate | log(rate) 対 PSNR の3次多項式、重なる PSNR 範囲で積分（`scripts/bdrate.py`） |
| 生データ | [bench.csv](bench.csv) |

時間はプロセスの起動から終了まで（CelV2 は CUDA の初期化を含む）。CPU 時間はエンコーダのプロセスが使った CPU 時間で、CelV2 の GPU の処理は含まない。計測中は別のセッションが avmenc を約36本動かしていた。ただし AVM の CPU 時間は実時間とほぼ同じ（例: 711.4 s に対し 707.8 s）なので、CPU の奪い合いによる実時間の水増しはほとんどない。

## 気づいたこと

1. **画質差の主な原因は、CelV2 にないツール**。CelV2 が持っていないものは次のとおり。
   - ループフィルタ: デブロック、CDEF、LR
   - 変換: DCT だけ（ADST と IDTX がない）
   - 動きベクトル: 整数画素だけで、参照は1枚だけ
   - 判定: SATD と概算ビットによるもので、実際の符号量を使う RDO はしていない
   - 量子化: 単純なデッドゾーンで、トレリスがない

   どれがどれだけ効いているかは、まだ切り分けていない。
2. **64点変換は低い方の32周波数だけを残す**（AV2 の zero-out）。64x64 ブロックを選ぶと、高い周波数がまるごと捨てられる。CelV2 の判定は SATD で行うので、この損失が見えない。テスト素材ではこれが原因で PSNR が約30 dB で頭打ちになった（Task 5 のメモ）。対策の候補は2つ：判定に zero-out を反映させる、または64を32x32の変換に分ける。
3. **P フレームの参照には復元画像が必要だった**。原画を参照にして動き探索とコスト計算をすると、符号化誤差が見えない。その結果、64x64 の inter ブロックが固定されたまま、7枚の P フレームで 37.5 dB から 30.4 dB まで落ちていった。復元画像を参照にするよう直したところ、38.9 dB を保つようになった（最終レビューの修正、`ippp_quality_holds`）。
4. **λ はまだ調整していない**。`lambda_q8 = 0.0005 × qstep² × 256` は仮の値で、ビット数は概算（モード2〜3ビット、分割2ビット）。λ と量子化の丸めの調整がどれだけ効くかは、まだ計っていない。
5. **計測スクリプトの不具合を直した**。ffmpeg の rawvideo 入力は既定で 25 fps として扱われる。そのため 30 fps の y4m とは、フレームがずれたまま比較されていた（どの Q でも PSNR が約27 dB）。`setpts=N` をかけても、2つの入力のタイムベースが違うので揃わない。今は rawvideo に y4m と同じフレームレートを渡している。表の PSNR は、保存してあったストリームを修正後の方法で計り直した値で、ビット数と時間は計測時の値のまま。

## 次の小プロジェクトの候補

1. **デブロック（と CDEF）**。デコーダ側の処理なので、AVM の av2/common をそのまま使える。ビット一致を保ったまま画質を上げやすい。
2. **小数画素 MV**。動きの多い素材で P フレームのビット数を大きく減らせる見込み。MVD はすでに QTR_PEL 精度で書いている。
3. **復元の GPU 化**。今は CPU の復元を待ってから次の判定に進む。復元を GPU に移すか、判定と復元を重ねて動かせば、1枚あたりの時間がさらに縮む。
4. **判定の改善**。λ の調整、64点変換の zero-out を判定に反映、ADST の追加。
